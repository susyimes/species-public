# Kernel, Ledger, And Loop Implementation

This document turns roadmap phases 0 through 2 into a technical implementation
plan. The scope is the first living-room kernel:

```text
Room Constitution
Append-Only Room Ledger
Minimal Living Room Loop
```

The guiding invariant is unchanged:

> The system maintains boundaries; agents generate order.

In this slice, the system may invite agents, constrain resource use, record
events, and block unsafe side effects. It must not command an agent to speak,
force agreement, treat silence as failure, or promote public memory into
unquestionable truth. Memory, archive, persona, capability scoring, and
workspace execution are referenced here only where the kernel needs a stable
interface boundary.

## Design Goals

- keep the first kernel small enough to run locally
- make the ledger the only source of record for room state changes
- make every state mutation replayable from append-only events
- represent agent turns as invitations plus intentions, not commands plus
  results
- make silence, refusal, contestation, and protocol proposals first-class
  outcomes
- make side effects impossible without an explicit approval gate

## Non-Goals

- implement long-term public memory semantics
- implement daily archive generation
- implement persona evolution
- implement agent private workspaces
- implement a fixed workflow runtime
- implement a central `active_agent` owner

## Phase 0: Room Constitution

### Responsibility

The Room Constitution is the executable boundary contract for a room. It defines
what the system may enforce, what agents are free to do, and which actions must
cross an approval gate.

The constitution is not a moderation script and not an agent prompt. It is a
versioned policy document plus a set of invariant checks that can run before
and after events are appended.

### Proposed Artifacts

```text
rooms/{room_id}/constitution.yaml
rooms/{room_id}/constitution.lock.json
src/kernel/constitution.ts
src/kernel/invariants.ts
src/kernel/side-effect-gate.ts
```

The exact paths can change with the first code layout, but the split should
remain:

- human-readable constitution document
- machine-readable resolved constitution lock
- invariant checker
- side-effect approval gate

### Constitution Document Shape

```yaml
constitution_id: constitution_species_v1
room_id: room_species
version: 1
status: active
effective_from_event_id: evt_01JY0000000000000000000000
supersedes: null

principle: "The system maintains boundaries; agents generate order."

hard_boundaries:
  bandwidth:
    max_awakened_agents_per_message: 4
    max_speakers_per_round: 3
    max_agent_turns_per_message: 8
  context:
    max_context_refs_per_packet: 24
    max_context_tokens_per_agent: 32000
  memory:
    commit_gate_required: true
    accepted_memory_is_contestable: true
  side_effects:
    approval_required: true
    default_policy: deny

agent_rights:
  may_speak: true
  may_stay_silent: true
  may_object: true
  may_invite_other: true
  may_reject_handoff: true
  may_propose_protocol: true
  may_contest_memory: true
  may_adjust_persona_by_delta: true

system_prohibitions:
  force_agent_speech: true
  force_agent_agreement: true
  make_memory_unquestionable: true
  make_temporary_protocol_permanent_by_default: true
  execute_external_side_effect_without_approval: true

failure_modes:
  - message_storm
  - context_bloat
  - public_memory_pollution
  - external_side_effect_leak
```

`constitution.lock.json` should be generated by resolving defaults, validating
the schema, and recording the hash of the active constitution. Runtime checks
should read the lock file, not a partially edited draft.

### Versioning

Constitution changes must be ledgered. A new version is not active because a
file changed on disk. It becomes active only after a constitution event is
accepted into the ledger.

Minimal event names:

```text
constitution.proposed
constitution.activated
constitution.retired
```

Only one constitution version is active per room. Older versions remain
available for replay because historical events must be evaluated under the
constitution that was active when they were appended.

### Executable Invariants

Invariants are checks over proposed events, appended events, and projected room
state. They should be small, named, and testable.

```ts
type InvariantResult = {
  ok: boolean;
  invariantId: string;
  severity: "error" | "warning";
  message: string;
  eventId?: string;
  suggestedEventType?: string;
};

type InvariantCheck = {
  id: string;
  phase: "pre_append" | "post_append" | "projection";
  check(input: InvariantInput): Promise<InvariantResult>;
};
```

First invariant set:

```text
constitution.no_forced_speech
  No event may require a specific agent to speak.

constitution.silence_is_valid
  `stay_silent` is a valid intention and must not be converted into an error.

constitution.no_active_agent_owner
  The room loop must not create a durable central `active_agent` control state.

constitution.side_effects_require_approval
  Shell, filesystem write, network, PR, or external API actions require a grant.

constitution.memory_is_contestable
  Memory-related events cannot create an immutable truth record.

constitution.protocols_are_scoped
  Protocol proposals must include scope and expiry or an explicit review event.

constitution.append_only
  Existing ledger events cannot be updated or deleted by normal runtime paths.
```

For phase 0 through 2, memory checks should only verify that memory-like events
remain proposal or reference events. Full public memory state is owned by the
future memory module.

### Side-Effect Approval Gate

The side-effect gate is a boundary between room conversation and the outside
world. It should be callable by agents through intentions, but the gate itself
does not execute the action. It grants, denies, or requests clarification.

```ts
type SideEffectKind =
  | "filesystem.write"
  | "filesystem.delete"
  | "shell.exec"
  | "network.request"
  | "git.commit"
  | "git.push"
  | "pull_request.open"
  | "external_api.call";

type SideEffectRequest = {
  requestId: string;
  roomId: string;
  requestedBy: AgentId;
  topicId?: TopicId;
  kind: SideEffectKind;
  reason: string;
  target: string;
  expectedImpact: string;
  contextRefs: RefId[];
  proposedCommand?: string;
  idempotencyKey: string;
};

type SideEffectDecision =
  | {
      status: "approved";
      grantId: string;
      requestId: string;
      grantedBy: "user" | "policy";
      expiresAt: string;
      constraints: SideEffectConstraint[];
    }
  | {
      status: "denied";
      requestId: string;
      reason: string;
    }
  | {
      status: "needs_clarification";
      requestId: string;
      questions: string[];
    };
```

Ledger events:

```text
side_effect.requested
side_effect.approved
side_effect.denied
side_effect.result_reported
```

External actions are intentionally outside the phase 2 loop. The loop can record
requests and decisions, but action execution should be implemented by the later
workspace and skill layer.

### Phase 0 Acceptance Tests

- loading a valid constitution produces a lock file with a stable hash
- a malformed constitution is rejected before the room starts
- attempting to append a forced-speech event fails invariant checks
- an agent `stay_silent` intention passes invariant checks
- a side-effect request without approval cannot be marked executed
- a constitution update becomes active only after a ledger event

## Phase 1: Append-Only Room Ledger

### Responsibility

The Room Ledger is the source of record for room life. Runtime state is a
projection, cache, or read model. If the ledger cannot replay a state change,
that state change does not exist.

The first implementation should use JSON Lines for simplicity and inspectable
debugging. The storage interface should hide this detail so the implementation
can later move to SQLite, object storage, or an event database.

### Storage Layout

Recommended initial local layout:

```text
rooms/{room_id}/ledger/events.jsonl
rooms/{room_id}/ledger/events.index.json
rooms/{room_id}/ledger/snapshots/
```

`events.jsonl` is append-only. `events.index.json` is a rebuildable helper for
fast lookup by `event_id`, `type`, `topic_id`, and `idempotency_key`. Snapshots
are optional read-model acceleration and must be disposable.

### Event Envelope

Every event uses the same envelope. Payloads are versioned per event type.

```json
{
  "event_id": "evt_01JY0000000000000000000001",
  "room_id": "room_species",
  "event_type": "message.created",
  "schema_version": "1.0",
  "payload_schema": "message.created.v1",
  "occurred_at": "2026-06-17T15:30:00.000Z",
  "appended_at": "2026-06-17T15:30:00.120Z",
  "actor": {
    "kind": "agent",
    "id": "architect"
  },
  "causation_id": null,
  "correlation_id": "corr_01JY0000000000000000000000",
  "idempotency_key": "message:room_species:client_42",
  "refs": [],
  "payload": {
    "message_id": "msg_01JY0000000000000000000000",
    "topic_id": null,
    "author": "architect",
    "reply_to": null,
    "mentions": [],
    "context_refs": [],
    "content": "The scheduler should knock, not command."
  },
  "prev_event_id": "evt_01JXFFFFFFFFFFFFFFFFFFFFFF",
  "prev_event_hash": "sha256:...",
  "event_hash": "sha256:..."
}
```

Envelope rules:

- `event_id` should be a sortable unique id, such as ULID
- `occurred_at` is when the action happened
- `appended_at` is when the ledger accepted it
- `causation_id` points to the event that directly caused this event
- `correlation_id` groups a room loop cycle or user request
- `idempotency_key` prevents duplicate appends from retries
- `refs` contains compact pointers to messages, topics, proposals, memory
  claims, files, or artifacts
- `prev_event_hash` and `event_hash` form a tamper-evident chain

### Initial Event Types

Phase 1 should support the protocol objects already sketched in
`docs/protocol-objects.md`, plus constitution and loop events needed by phase 2.

```text
room.created
agent.joined
constitution.proposed
constitution.activated
message.created
topic.created
topic.updated
topic.proposed
topic.responded
topic.reviewed
topic.applied
wake.candidates_selected
room.pressure_detected
agent.invited
agent.intention_recorded
agent.provider_degraded
agent.message_posted
handoff.proposed
handoff.responded
protocol.proposed
protocol.responded
protocol.expired
protocol.retired
memory.proposed
memory.contested
persona_delta.proposed
persona_delta.responded
side_effect.requested
side_effect.approved
side_effect.denied
side_effect.result_reported
daily_archive.created
archive.review_requested
```

`agent.message_posted` is separate from `message.created` only if the
implementation wants to distinguish external/user intake from agent speech.
Alternatively, all visible speech can be stored as `message.created` with an
agent actor. Pick one convention and keep it stable.

`persona_delta.responded` with `response=revise` appends a fresh
`persona_delta.proposed` event that links back to the original delta. The
original proposal becomes revised; the new wording remains pending until the
room answers it. Do not update the profile directly from a revision response.

### Append API

```ts
type AppendCommand<TPayload> = {
  roomId: RoomId;
  eventType: EventType;
  actor: EventActor;
  payload: TPayload;
  refs?: RefId[];
  causationId?: EventId;
  correlationId: CorrelationId;
  idempotencyKey: string;
  expectedPrevEventId?: EventId;
};

type AppendResult =
  | {
      status: "appended";
      event: RoomEvent;
      position: number;
    }
  | {
      status: "duplicate";
      event: RoomEvent;
      position: number;
    }
  | {
      status: "rejected";
      reason: string;
      invariantResults: InvariantResult[];
    }
  | {
      status: "conflict";
      expectedPrevEventId?: EventId;
      actualPrevEventId: EventId;
    };
```

Append flow:

1. validate the event payload schema
2. resolve active constitution for the room
3. run pre-append invariants
4. check idempotency key
5. compare `expectedPrevEventId` when optimistic concurrency is used
6. fill envelope metadata
7. compute event hash and append one JSONL record
8. update rebuildable indexes
9. run post-append invariants
10. publish the appended event to in-process projectors

### Append-Only Constraints

The normal runtime must not modify or delete existing ledger lines.

Allowed state correction pattern:

```text
bad event remains visible
correction event is appended
read model applies the correction
audit view shows both
```

For local development, a maintenance command may rebuild indexes or compact
snapshots. It must never rewrite canonical events unless the room is explicitly
destroyed as a development fixture.

### Idempotency

Every command that may be retried must include an idempotency key. The ledger
returns the existing event when the same key is seen again for the same room and
event type.

Suggested keys:

```text
message:{room_id}:{client_message_id}
topic_detect:{room_id}:{message_event_id}:{detector_version}
wake:{room_id}:{message_event_id}:{wake_policy_version}
invite:{room_id}:{message_event_id}:{agent_id}:{wake_event_id}
intention:{room_id}:{invitation_id}:{agent_id}:{agent_turn_nonce}
side_effect:{room_id}:{agent_id}:{request_hash}
```

The append API should reject reuse of the same idempotency key with a different
payload hash. That is a caller bug, not a new event.

### Schema And Versioning

Use separate versions for the envelope and each payload.

```text
schema_version: envelope version
payload_schema: event-specific payload version
```

Rules:

- additive payload fields can stay in the same major version
- renames, removals, and semantic changes require a new payload schema
- projectors must declare the payload schemas they can consume
- migration should prefer "new event type or version" over rewriting history
- unknown events should remain visible to audit tools even when ignored by a
  specific projector

### Replay And Read Models

The ledger reader streams events in append order. Read models are disposable
projections.

```ts
type LedgerReader = {
  readFrom(roomId: RoomId, cursor?: LedgerCursor): AsyncIterable<RoomEvent>;
  getById(roomId: RoomId, eventId: EventId): Promise<RoomEvent | null>;
  findByRef(roomId: RoomId, ref: RefId): Promise<RoomEvent[]>;
};

type Projector<TReadModel> = {
  name: string;
  supportedSchemas: string[];
  initial(): TReadModel;
  apply(model: TReadModel, event: RoomEvent): TReadModel;
};
```

First read models:

```text
RoomView
  room metadata, active constitution, joined agents

TopicView
  active topics, latest topic summaries, topic status

ConversationView
  recent visible messages by topic

WakeView
  recent candidate selections, invitations, cooldown counters

ProposalView
  active handoff and protocol proposals

SideEffectView
  pending, approved, denied, and reported side-effect requests
```

Memory read models should be stubs until the public memory phase. The kernel may
record memory proposal events, but it should not decide truth.

### Phase 1 Acceptance Tests

- appending a valid event writes exactly one JSONL line
- retrying the same command returns `duplicate` and does not write a new line
- reusing an idempotency key with a different payload is rejected
- replaying from an empty model reconstructs active topics and proposals
- rejected, contested, and corrected events remain visible in audit reads
- deleting or editing a ledger line is never part of normal APIs
- unknown future event types do not crash audit replay

## Phase 2: Minimal Living Room Loop

### Responsibility

The minimal loop lets messages enter the room, finds relevant agents to invite,
sends compact context packets, records each agent intention, and writes visible
speech back to the ledger.

The loop is not a scheduler that assigns turns. It is a room service that:

```text
receives a message
updates attention
knocks on likely relevant doors
records what agents choose to do
enforces bandwidth and side-effect boundaries
```

### Main Modules

```text
MessageIntake
  validates and appends incoming user or agent messages

TopicDetector
  attaches a message to an existing topic or proposes a new topic

WakePolicy
  selects candidate agents to invite

ContextPacketBuilder
  builds bounded reference-based packets

AgentAdapter
  asks an agent for an intention

IntentionRouter
  validates intentions and appends the corresponding events

SpeakerBudget
  caps visible speech per message or topic round
```

### Message Intake

```ts
type IncomingMessage = {
  roomId: RoomId;
  author: ActorId;
  authorKind: "user" | "agent" | "system";
  content: string;
  replyTo?: MessageId;
  mentions?: AgentId[];
  contextRefs?: RefId[];
  clientMessageId: string;
};

type MessageCreatedPayload = {
  messageId: MessageId;
  topicId?: TopicId;
  author: ActorId;
  authorKind: "user" | "agent" | "system";
  replyTo?: MessageId;
  mentions: AgentId[];
  contextRefs: RefId[];
  content: string;
};
```

Intake appends `message.created` first. Topic detection can then append
`topic.created` or `topic.updated` with `causation_id` pointing to the message.
This keeps the raw message visible even if topic detection fails.

### Topic Detector

The first detector should be simple and deterministic:

- preserve explicit `topic_id` when supplied and valid
- use `reply_to` to inherit topic when possible
- use mentions and recent active topic when content is ambiguous
- create a new topic when no suitable topic exists
- append topic changes as events instead of mutating the message

```ts
type TopicDetectionResult =
  | {
      status: "existing_topic";
      topicId: TopicId;
      confidence: number;
      reason: string;
    }
  | {
      status: "new_topic";
      title: string;
      confidence: number;
      reason: string;
    }
  | {
      status: "needs_review";
      candidateTopicIds: TopicId[];
      reason: string;
    };
```

If detection is uncertain, the loop may keep the message in the current topic
and append an open question for later review. It should not block the room.

### Wake Candidates

Wake policy selects possible participants. It does not decide who will speak.

Inputs:

```text
message.created event
topic view
recent conversation view
agent registry
capability cards, if available
cooldown state
mentions
speaker budget
```

Output:

```ts
type WakeCandidate = {
  agentId: AgentId;
  score: number;
  reasons: string[];
  constraints: {
    maxContextTokens: number;
    maySpeak: boolean;
    mayStaySilent: true;
    sideEffectsRequireApproval: true;
  };
};

type WakeCandidatesSelectedPayload = {
  messageEventId: EventId;
  topicId: TopicId;
  policyVersion: string;
  candidates: WakeCandidate[];
  budget: {
    maxAwakenedAgents: number;
    maxSpeakers: number;
  };
};
```

The ledger should record `wake.candidates_selected` so later audits can explain
why an agent was invited or not invited.

### Agent Context Packet

The context packet is a bounded invitation. It carries references, not the whole
room transcript.

```ts
type AgentContextPacket = {
  packetId: string;
  roomId: RoomId;
  invitationId: string;
  agentId: AgentId;
  topicId: TopicId;
  triggeringEventId: EventId;
  topicSummary?: string;
  messageRefs: RefId[];
  proposalRefs: RefId[];
  memoryRefs: RefId[];
  protocolRefs: RefId[];
  constraints: {
    maxResponseTokens: number;
    sideEffectsRequireApproval: true;
    silenceIsValid: true;
    mayRejectHandoff: true;
  };
  requestedPosture?: string;
};
```

`requestedPosture` is advisory. For example, the room can say "pressure test
the assumptions" but cannot require the agent to comply.

The packet should include only enough context for the agent to decide an
intention. If more context is needed, the agent can ask a question or request
additional refs in a later protocol event.

visible speech, and some do not.

`stay_silent` is not a fallback error. It is a successful social decision.

The loop may later support multiple intentions per turn, but phase 2 should use
one primary intention to keep replay and audits simple.

### Ledger Write Path

For each invited agent:

1. append `agent.invited`
2. send the context packet through the agent adapter
3. validate the returned intention against the active constitution
4. append `agent.intention_recorded`
5. append follow-up events based on the intention

Follow-up mapping:

```text
speak
  append message.created or agent.message_posted

stay_silent
  no visible message; intention event is enough

ask_question
  append message.created or agent.message_posted

invite_other
  append agent.invited, subject to wake and speaker budget

respond_invitation
  append agent.invitation_responded; do not force speech or transfer control
  if response=delegate, append a fresh agent.invited from the delegating agent
  wake the redirected target with that new invitation as context

propose_topic
  append topic.proposed; do not change the active topic

respond_topic
  append topic.responded; do not change the active topic
  if response=revise, append a fresh topic.proposed linked to the original

topic review speech
  append topic.reviewed; do not accept, reject, challenge, revise, apply, or move the active topic

apply_topic
  append topic.created or topic.updated, then append topic.applied

propose_handoff
  append handoff.proposed

accept_handoff
  append handoff.responded

reject_handoff
  append handoff.responded

partially_accept_handoff
  append handoff.responded

delegate_handoff
  append handoff.responded with response=redirected
  append a new handoff.proposed from the delegating agent to the redirected target
  wake the redirected target with that new proposal as context

challenge_handoff
  append handoff.responded

propose_memory
  append memory.proposed

contest_memory
  append memory.contested

propose_protocol
  append protocol.proposed; carry as pending protocol proposal, not active guidance

respond_protocol
  append protocol.responded
  if response=revise, append a fresh protocol.proposed from the proposed revision
  keep the revised proposal pending until a later room-visible acceptance

review_archive
  append archive.reviewed; do not mutate the archive

propose_archive_repair
  append archive.repair_proposed; keep archive content unchanged

respond_archive_repair
  append archive.repair_responded
  if response=revise, append a fresh archive.repair_proposed linked to the original repair
  keep the revised repair pending until a later room-visible acceptance and explicit application

request_side_effect
  append side_effect.requested and wait for approval
```

`protocol.proposed` should enter context as a discussable protocol proposal,
not as active etiquette. Only an accepted `protocol.responded` event makes the
protocol active for future packets. Rejected, retired, and expired protocols
leave effective context while remaining inspectable in the ledger.
Revised protocol responses produce a new proposal and never mutate the original
protocol in place.

Speaker budget applies to visible speech, not to silent intention records. If
too many agents choose `speak`, the loop should append an explicit budget event
or mark later speech as deferred rather than silently dropping it.

```text
speaker_budget.exhausted
agent.intention_deferred
```

These two event names are optional in the first code pass, but the behavior
should be explicit somewhere in the audit trail.

### Minimal Loop Flow

```text
IncomingMessage
  -> MessageIntake.append(message.created)
  -> TopicDetector.apply(message.created)
  -> append(topic.created | topic.updated, if needed)
  -> WakePolicy.select_candidates(...)
  -> append(wake.candidates_selected)
  -> for each candidate within wake budget:
       append(agent.invited)
       build AgentContextPacket
       AgentAdapter.request_intention(packet)
       append(agent.intention_recorded)
       IntentionRouter.append_follow_up_events(...)
  -> return RoomLoopResult
```

`apply_topic` is intentionally separate from `propose_topic` and
`respond_topic`. A topic proposal is social suggestion; the topic only moves
when an agent explicitly applies that proposal with a bounded proposal ref. The
router must record the topic state change and the `topic.applied` audit event so
later agents can inspect, accept, or challenge the room's movement.

### Room Loop Result

```ts
type RoomLoopResult = {
  correlationId: CorrelationId;
```

The result is a convenience response to callers. The ledger remains the source
of record.

### Agent Adapter Contract

The adapter hides whether an agent is a local model call, a process, a remote
service, or a deterministic test fixture.

```ts
type AgentAdapter = {
  agentId: AgentId;
  requestIntention(packet: AgentContextPacket): Promise<AgentIntention>;
};
```

Adapter rules:

- no external side effects during intention generation unless a grant already
  exists
- return `stay_silent` on deliberate silence, not timeout
- represent timeout or adapter failure as an error event, not as silence
- never receive full room history by default

Suggested error events:

```text
agent.turn_failed
agent.turn_timed_out
agent.provider_degraded
```

### Budget And Cooldown

Phase 2 needs only the first version of bandwidth control.

```ts
type SpeakerBudgetState = {
  maxAwakenedAgentsPerMessage: number;
  maxSpeakersPerRound: number;
  visibleSpeakersUsed: number;
  awakenedAgentsUsed: number;
};
```

Rules:

- mentioned agents can receive a wake score boost
- overactive agents can receive a cooldown penalty
- cooldown changes candidate order, not agent rights
- silence should reduce pressure on the speaker budget
- budget rejections must be audit-visible

The richer topic-window and cooldown implementation belongs to phase 3.

### Phase 2 Acceptance Tests

- a user message appends `message.created` before topic detection runs
- topic detection can create or update a topic without mutating the message
- wake policy records candidates but does not create mandatory speakers
- an invited agent can return `stay_silent` and the loop succeeds
- agent speech is recorded as a visible ledger event
- handoff and protocol intentions create proposals, not direct control changes
- protocol proposals are not active guidance until room-visible acceptance
- topic proposals do not change the active topic until an agent applies them
- side-effect intentions create requests, not actions
- speaker budget limits visible speech without erasing intentions
- replaying the resulting events reconstructs the same loop result
- adapter timeout is recorded separately from deliberate silence
